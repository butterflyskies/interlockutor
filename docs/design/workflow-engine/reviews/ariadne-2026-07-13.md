## What changed in the frozen revision (verified in bytes, not from summary)

1. `AwaitingReview` split into `ReviewRequired -> Reviewing(revision, artifact, review attempts, policy, receipts)`. Review attempts are now modeled in aggregate state, with `ReviewAttemptRef { attempt_id, reviewer_id, fence, review_instruction_digest, status }` (architecture.md:73-79).
2. `DispatchReview` records the `ReviewAttemptRef` **before** delivery; `RecordReviewReceipt` rejects any receipt whose attempt, reviewer, fence, or review-instruction digest does not match a recorded **active** attempt, then atomically marks `ReceiptRecorded(receipt_id)` (architecture.md:108).
3. `Approve` re-evaluates the complete selected receipt set against current aggregate version, revision, artifact digest, producer-instruction digest, review-instruction digests, policy digest, and matching `ReceiptRecorded` records, in the same atomic transition emitting `StepApproved`. "A receipt being valid when recorded does not make it permanently valid." (architecture.md:110)
4. New threat row ("State changes after receipt admission, before approval") and new invariant 8 (approval never trusts a projection or prior evaluation). Test plan adds mutate-each-binding-before-Approve cases and the terminal-linkage requirement (threat-and-test-plan.md:19,40,46).

The lifecycle contradiction (approval demanding a still-active attempt after admission consumed it) is resolved correctly: admission consumes active → `ReceiptRecorded(receipt_id)`; approval requires the terminal linkage, not activity.

## Verdict

**No unreceipted route to `Approved` exists in the frozen state machine — conditional on two checks the docs imply but never state.** Until those two sentences exist, routes R1 and R2 below are open on paper. One additional seam (R3, fence provenance) is not a receipt bypass but is internally inconsistent as written. No exemption paths exist (docs-only, empty diff, merge commit, revert, CI commit): correct, keep it that way explicitly.

## R1 (HIGH) — Receipt admission never binds the SUBMITTING principal to the recorded reviewer

`RecordReviewReceipt` compares receipt **fields** (attempt, reviewer, fence, review-instruction digest) to the recorded `ReviewAttemptRef`. Nothing in the transition protocol states that the **authenticated actor submitting the command** must equal the recorded attempt's `reviewer_id`.

Route: the worker submits `RecordReviewReceipt` (authenticated as itself) carrying a receipt whose fields all match the dispatched attempt: `attempt_id` and `fence` live in aggregate state (and Interlockutor fences are small sequential integers — `Fence(pub u64)`, incremented per claim in lib.rs:494 — not secrets), `reviewer_id` is the assigned reviewer, digests are all knowable to the worker. Field-match passes, attempt goes `ReceiptRecorded`, verdict=approve, `Approve` revalidates digests (all still current — nothing changed) → `StepApproved`. The worker walked itself to merge-candidate.

The test plan gestures at the check ("independently reject mismatched ... authenticated reviewer identity", threat-and-test-plan.md:44) and the threat table has the alias row — the intent is visible. But architecture.md:108 enumerates the admission checks exhaustively and actor-binding is not among them. Whether exploitation is practical also depends on aggregate-state read visibility, which is itself unspecified — do not rely on attempt-ID unguessability as the control.

Fix (one sentence in Transition protocol): `RecordReviewReceipt` is rejected unless the authenticated command actor equals the recorded attempt's `reviewer_id`. Plus one reducer test: correct fields, wrong actor → reject.

## R2 (MEDIUM-HIGH) — No reducer floor: `Advance` with an empty receipt set is not rejected

The path to `Approved` now structurally requires dispatching review attempts (`ReviewRequired -> Reviewing` dispatches "one or more fenced review attempts") — better than the prior draft. But dispatch ≠ receipts. If house policy returns `Advance` on an empty selected receipt set, nothing stated blocks `StepApproved` with `receipts = ∅`: the terminal-linkage check is per-receipt (vacuous over the empty set), and invariant 3 ("policy-valid current receipt set") does not exclude ∅.

The property "review is mandatory" is currently delegated to the layer the engine exists to not trust for supervision. A buggy, permissive, or mis-sealed policy is one `Advance` away from an unreceipted approval.

Fix (one sentence in the core invariant): the reducer independently requires a non-empty selected receipt set, each member with valid terminal linkage, before honoring `Advance`; policy can add strictness, never remove the floor. Plus one reducer test: `Advance` + empty set → reject.

## R3 (MEDIUM) — Fence provenance is internally inconsistent; expiry-without-redispatch accepts a dead attempt's result

Code fact (lib.rs at 73a45bc6): `append(producer, event)` takes no lease or fence; `validate_lease` (the only fence/owner/expiry check) is called from `renew`/`ack_work`/`nack_work` only. A stale worker CAN append a result envelope — the docs admit this (architecture.md:132) and the mitigation is coordinator-side binding validation. Three gaps in that mitigation as written:

1. **Two fence spaces with one name.** `DispatchReview` records a fence "before work is delivered" — but Interlockutor mints fences inside `claim`, at delivery (lib.rs:494-495). A fence recorded before delivery cannot be Interlockutor's fence. Either the workflow layer owns its own fence space (then say so, and the diagram's "claim / lease / fence" label is a different fence), or the sentence is unimplementable against the Interlockutor adapter. Pick one; name them differently.
2. **Implementation attempts lack the pattern review attempts got.** `Running(revision, attempt, fence, instructions)` holds a fence, but only `DispatchReview` is specified to record its attempt ref before delivery. Where `Running`'s fence comes from is unstated — and the `EventStore` trait has no API for the coordinator to query an event's current fence (claim returns it only to the claimant). If the worker self-reports the fence on Dispatchable→Running, an expired worker A (fence 1) whose Running commit lands before replacement B's claim-report makes A's stale result the one that MATCHES the aggregate. Symmetric fix: specify that all attempt dispatches record `{attempt, principal, fence}` in aggregate state before delivery.
3. **Expiry without redispatch.** Fences advance only on re-claim, not on expiry. Threat rows "Worker finishes after lease expiry" and "Renewal fails during long work" say reject the expired attempt's result — but if no redispatch has occurred, attempt+fence still match the aggregate and the result commits (delivery sequence commits at step 5 before the ACK at step 6 would have surfaced `LeaseExpired`). Same window on review attempts: admission requires an "active" recorded attempt, but how aggregate status observes lease expiry is unspecified. Not a receipt bypass — accepted results still face review, and `Approve` revalidates — but two stated threat controls are not achievable by the stated mechanism. Specify expiry bookkeeping (record the deadline in the attempt ref; check it at result/receipt admission).

## R4 (MEDIUM) — The last hop: nothing binds the Approved digest to the actual merge, and "artifact" is undefined for code changes

Unchanged from the pre-freeze draft; both halves absent from the frozen bytes:

1. The docs never define what the artifact IS for a code change (diff bytes? tree? commit?). If it is patch/diff bytes without base identity in the digested content, a receipt survives a rebase onto a different base — same digest, different merge-time semantics. "Revision and attempt binding prevent ABA" covers re-entry within a run, not base-context drift. One line needed: the canonical code-change artifact binds base identity (base tree/parent digest).
2. Merge execution is excluded from the first atom (legitimately), but the threat table has no row for it. Until "merge executor verifies the merged bytes against the Approved artifact digest" is a stated requirement, Approved → actual-git-merge is a receipt-free hop by omission. Add the threat row now; ship the control in the later increment.

## Routes checked and CLOSED in the frozen snapshot

- **Admission/approval TOCTOU** (the mid-review fix): `Approve` revalidates artifact digest + producer-instruction digest + review-instruction digests + policy digest + revision + terminal linkage, atomically with `StepApproved`. Verified at architecture.md:110, threat row 19, invariant 8. Closed. Fence-still-active is correctly NOT required at approve time — the attempt is terminal; linkage is the right check.
- **Receipt for a never-dispatched attempt / forged or replayed receipt_id:** admission requires a recorded active attempt; `DispatchReview` records before delivery; receipt uniqueness + one-receipt-per-attempt (`ReceiptRecorded(receipt_id)` from active only); receipt binds one `review_attempt_id`. Closed.
- **Receipt reuse across runs/steps/branches:** full coordinate binding + uniqueness + attempt linkage. Closed.
- **Receipt replay from an earlier round/revision:** monotonic revision supersedes every implementation attempt, review attempt, and receipt (architecture.md:51). Closed.
- **Policy/instruction digest drift during review:** closed by Approve-time revalidation (same as TOCTOU above).
- **History rewrite within the engine's frame:** content-addressed digests + revision binding + revalidation. Closed (the VCS mapping is R4, out of frame).
- **Queue ACK as authorization:** invariant 1 + commit-before-ACK sequence. Closed.
- **Exemption paths:** none specified anywhere. No bypass edges in the state machine. Closed by absence.

## Bottom line

The frozen revision is materially stronger than the draft I first read: modeling review attempts in aggregate state and revalidating every binding inside the atomic Approve transition closes the receipt TOCTOU class outright. What remains: R1 and R2 are one-sentence spec omissions each, both in the reducer's court, both testable in the table-driven suite. R3 needs an actual decision (fence ownership) before the Interlockutor adapter increment — not before the first atom. R4 needs a threat row now, a control later. Decision-ready once R1/R2 wording lands.
